# Windows 작업 스케줄러로 세션 백업을 자동화하며 경고를 실패로 처리한 문제

## 이번에 한 작업

로컬에 쌓이는 AI 코딩 세션을 매일 백업하고 원격 저장소까지 동기화하는 작업을 Windows 작업 스케줄러에 등록했다. 목표는 단순히 예약을 거는 것이 아니라, 백업 과정이 실패했을 때 어느 단계에서 멈췄는지 다시 확인할 수 있게 만드는 것이었다.

실행 흐름은 다음처럼 나눴다.

- 예약 작업은 얇은 runner 스크립트만 실행
- runner는 세션 내보내기와 Git 동기화를 담당하는 스크립트를 호출
- 동기화 스크립트는 최신화, 두 종류의 세션 export, 변경 파일 검사, commit, push를 순서대로 처리
- 변경이 없으면 commit하지 않고 종료

예약 작업에는 관리자 권한을 요구하지 않고, 현재 사용자 권한으로 실행되게 설정했다.

## 처음에는 실행됐는데 push가 되지 않았다

작업 스케줄러에서는 실행 이력이 남았고 세션 export도 실제로 수행됐다. 그런데 원격 저장소에는 새 commit이 없었다.

로그를 따라가 보니 Git의 줄바꿈 경고가 stderr로 출력된 것이 시작점이었다. Git 명령의 종료 코드는 0이었지만, PowerShell 쪽에서 stderr가 출력됐다는 사실 자체를 예외처럼 처리하면서 commit 단계 전에 중단됐다.

문제는 한 곳에만 있지 않았다.

1. Git을 호출하는 동기화 스크립트가 경고 출력과 실패를 충분히 구분하지 못했다.
2. 예약 runner도 자식 PowerShell의 경고 스트림을 받아 실패로 판단했다.

즉 안쪽 스크립트만 고쳐서는 예약 실행이 계속 실패할 수 있는 구조였다.

## 적용한 수정

Git 실행 부분은 stderr 유무가 아니라 프로세스 종료 코드로 성공 여부를 판단하도록 바꿨다. 경고 출력은 로그에 남기되, 종료 코드가 0이면 다음 단계로 진행한다.

runner도 같은 기준으로 정리했다. 자식 프로세스의 출력은 기록하되, 실제 실패는 non-zero 종료 코드일 때만 전파하도록 분리했다. 이렇게 하니 진짜 실패는 놓치지 않으면서도 줄바꿈 안내 같은 비치명 경고 때문에 백업 전체가 멈추지 않았다.

또한 실패 중간에 남아 있던 아카이브 변경은 스크립트 수정과 섞지 않고 먼저 별도 commit으로 보관했다. 데이터 백업과 도구 수정의 원인을 나중에 구분하기 쉬워진다.

## 검증한 방법

수정 뒤에는 세 단계로 확인했다.

- dry-run으로 export와 Git 호출 순서 확인
- 기존 테스트 전체 실행
- 예약 작업을 수동으로 한 번 실행해 최종 종료 결과 확인

테스트는 8개가 모두 통과했고, 수동 실행도 성공 종료됐다. 작업 스케줄러 상태와 다음 실행 예정 시각도 함께 확인해, 스크립트만 정상이고 예약 등록이 잘못된 경우를 분리했다.

## 정리

자동화에서 stderr는 실패의 단서가 될 수 있지만 실패 자체는 아니다. 특히 Git처럼 경고를 stderr로 쓰는 도구를 PowerShell에서 감쌀 때는 출력 스트림과 종료 코드를 구분해야 한다.

이번 작업은 세션 백업을 예약한 기록이기도 하지만, runner와 실제 작업 스크립트가 두 겹일 때는 두 경계 모두에서 실패 판정을 검증해야 한다는 점을 확인한 작업이었다.
